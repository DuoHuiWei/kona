# 模块构建原则

日期：`2026-08-09`

本文用于约束后续新模块、新 benchmark、新对照实验的构建方式。  
核心目标不是统一代码风格，而是尽量避免 **实验口径差异**、**隐藏的不公平优化**、**模块职责不一致** 这些更危险的问题。

很多时候，程序可以正常编译、正常 PASS、数字也很好看，但实验已经在不知不觉中歪掉了。  
因此后续做任何新模块，都要优先遵守本文。

---

## 1. 总原则

后续新增模块、比较器、Top-k 网络、距离核、份额转换或 benchmark 时，必须默认满足以下原则：

1. 逻辑必须真实。
2. 通信必须真实。
3. 字节数必须真实。
4. 随机掩码、随机数、Beaver `a/b/c` 这类辅助材料，只有在用户明确允许 `L2` 风格检查时，才允许直接置零。
5. 优先复用现有 Kona/Garnet 组件，而不是重新发明一套新逻辑。
6. 如果原组件功能正确但并行化不够，可以新写并行化版本，但逻辑、接口、语义要尽量贴近原版，便于公平比较。

---

## 2. 新模块开工前，必须先问用户的问题

每次写新模块前，除非这些信息已经在当前线程中明确，否则应先问清楚。

### 2.1 功能边界

必须确认：

- 新模块到底要完成到哪一步。
- 是否只做到 compare。
- 是否要做到 compare + B2A。
- 是否要做到 compare + swap。
- 是否要做到 compare + top-k mask。
- 是否要做到完整主路径。

如果两边对照模块完成的功能层级不一致，benchmark 就不成立。

### 2.2 目标对照对象

必须确认：

- 要和谁比较。
- 是和 Kona 原主路径比较。
- 是和 Cong 比较。
- 是和 DCF 比较器比较。
- 是和 PCR 比较器比较。
- 是和 Beaver 风格距离核比较。

### 2.3 预处理口径

必须确认：

- 是否计入 offline 时间。
- 是否计入 offline 通信。
- 是否计入落盘。
- 是否计入读取预处理文件时间。
- 在线 benchmark 是否假设预处理已经完成。

如果不先问清楚，最容易在“在线速度”和“整体代价”之间混口径。

### 2.4 批量粒度

必须确认用户希望的批量粒度：

- 只允许 within-vector batching。
- 是否允许 across-pair batching。
- 是否允许 across-layer batching。
- 是否允许一次性吞全部实例。
- 是否必须切成固定 chunk，例如 `16348`。

这一点极其重要，因为很多实验差异并不来自协议本身，而是来自批量策略不同。

### 2.5 网络口径

必须确认：

- 跑无额外延迟。
- 跑容器内 LAN。
- 跑容器内 WAN。
- 还是三者都要。

当前统一口径：

```text
纯本地口径 = 不加任何网络延迟 / 不施加额外 tc/netem 条件
```

这不等于通信耗时为 0，只是没有额外注入网络延迟。

### 2.6 数据口径

必须确认：

- 用真实数据集还是手工数据。
- 用哪个数据集。
- 比较规模是 `N`、`k`、维度多少。
- 是否允许重复值。
- 是否要求稳定 tie-breaking。

## 3. 完成后必须做的两类检查

每个新模块完成后，至少要做两类检查：

1. `堆糖检查`
2. `不公平检查`

这里“堆糖检查”沿用当前项目里的叫法，核心意思是：  
不要只看程序跑通，而要把模块实际堆叠出来的协议层、通信层、转换层、交换层，一层层剥开核对。

---

## 4. 堆糖检查

堆糖检查主要检查：代码虽然 PASS，但是否偷偷多做了一层、少做了一层、或者把某一步塞进了别的地方。

### 4.1 功能层级是否一致

必须核对：

- A 方案是否只做到 compare bit。
- B 方案是否已经做到 compare + B2A + swap。

最终必须统一到同一功能接口。

例如如果对照的是排序比较器，推荐统一成：

```text
([x], [y]) -> ([min], [max])
```

不能一边只停在 Boolean compare bit，另一边已经把选择交换也做完。

### 4.2 转换步骤是否藏在内部

必须问清楚并写明：

- B2A 是比较器内部做的，还是外部做的。
- A2B 是模块内部做的，还是上层做的。
- label vote 时是否又重复做了转换。

### 4.3 乘法范围是否一致

必须核对：

- 乘法是逐元素做。
- 是单 pair 内 batch。
- 还是跨 pair 合并。
- 是否用了 `double_res`。
- 是否同时处理 distance 和 label。

### 4.4 交换/排序是否真的发生

例如：

- Cong / legacy 是真的做了 `swap`
- matrix 是不交换，只做 rank + mask + vote

这在实验解释中必须明确写出来，不能混成“都是 top-k”。

### 4.5 主路径里到底算了什么

如果是 `kona.cpp` 主路径实验，必须写明：

- 是否生成了 `m_ESD_vec`
- 是否走了 top-k
- 是否走了 label vote
- 是否走了最终 winner 选择

---

## 5. 不公平检查

这是后续所有对照实验最重要的一类检查。

至少要审计以下 6 件事。

### 5.1 比的是不是同一个功能

必须确认：

- 两边最终比较的是同一个接口。
- 两边是否都包含 compare、B2A、swap、rank、vote 等相同层级。

### 5.2 并行粒度是不是一样

必须明确区分：

- within-vector batching
- across-pair batching
- within-layer batching

不能一边逐 pair 发消息，另一边整层合批，然后说后者轮次少。

### 5.3 预处理口径是不是一样

必须明确：

- offline 时间算不算
- offline 通信算不算
- 落盘算不算
- 读盘算不算
- online 是否假设预处理已经完成

### 5.4 安全参数和数据语义是不是一样

必须核对：

- 比较位宽是不是一样
- 都是 `u64` 还是一边其实只算 `u32`
- signed / unsigned 语义是不是一致
- ring 是不是一致
- 比较语义是不是一致，例如相等时谁赢

### 5.5 运行资源是不是一样

必须锁死：

- CPU 核数
- 线程数
- 是否开 OpenMP / Rayon / pthread
- 是否用 GPU
- 编译参数是否一致，例如 `-O3`
- 网络模拟方式是否一致

当前项目最近这批 `Kona / Cong / Matrix / PCR / DCF` benchmark 的默认运行资源口径，还应额外明确为：

```text
无绑核
无显式 OpenMP 多线程
无 taskset / affinity 约束
双进程并发
由操作系统自由调度到 CPU 核
```

也就是说，当前实验默认不是“严格单核”，也不是“我们主动实现的多核并行 benchmark”，而是：

```text
P0 / P1 两个进程同时运行，
各自主流程基本单线程，
由系统自由分配核心。
```

后续如果需要更严格的资源控制，应单独声明并固定成新的实验口径，例如：

- 绑定单核
- 绑定固定两个核
- 固定线程数
- 限制 OpenMP / pthread worker 数量

### 5.6 有没有一方吃了特殊优化

这是 AI 实现最容易悄悄出现的问题。

例如：

- 一边用了批量 socket buffer，另一边没有。
- 一边复用了中间状态，另一边每次重新申请内存。
- 一边用了 chunked batch，另一边还逐实例跑。
- 一边用了 `double_res`，另一边拆成两次乘法。

这些未必是 bug，但如果不写清楚，benchmark 就不公平。

---

## 6. 关于批量策略的专项检查

之后凡是涉及批量比较、批量转换、批量乘法，都要额外回答下面几个问题：

1. 是不是把所有任务一次性全吞掉了。
2. 是否支持固定 chunk。
3. 是否支持 tile / block。
4. 是否跨 pair 合批。
5. 是否跨 layer 合批。
6. 是否为了某个方案特别引入了更大的 batch，而另一方案没有。

当前项目中的默认经验规则是：

```text
除了 seq-ran / tcga 等 ESD 专项实验，
通用大批量 Beaver 乘法、份额转换、批量打开等动作，
默认优先按 chunk size = 16348 切分。
```

但这不是不可动的定律。  
只要实验目标不同，就必须重新说明批量策略。

---

## 7. 关于纯本地口径

之后所有文档、benchmark、口头说明都统一使用下面这套说法：

### 7.1 纯本地口径

```text
纯本地口径 = 不加任何额外网络延迟 / 不施加额外 tc / netem 条件
```

它表示：

- 不使用容器内 LAN 条件
- 不使用容器内 WAN 条件
- 只跑默认本机 / 容器内 localhost 通信

### 7.2 纯本地口径不等于零通信时间

必须明确：

```text
纯本地口径 != 通信时间为 0
```

因为仍然存在：

- 进程调度
- socket/TCP 栈
- octetStream 打包拆包
- 本机双进程同步等待

所以“无额外延迟”的 `comm_ms` 仍然可能很大。

### 7.3 如何解读 compute_ms

当前大部分 benchmark 中：

```text
compute_ms = total_ms - comm_ms
```

因此它更接近：

```text
非 send/receive 计时部分的残差
```

而不是严格意义上的：

```text
纯 CPU 算术时间
```

所以：

- `total_ms` 可以直接比
- `sent_bytes` 可以直接比
- `rounds` 可以直接比
- `comm_ms` 可以大体看通信成本
- `compute_ms` 只能作为“去掉 send/receive 后的剩余部分”来理解

## 8. 以后写新模块时，推荐的工作流

### 第一步：先问清楚口径

至少确认：

- 功能做到哪一步
- 与谁对照
- offline / online 怎么算
- 批量粒度怎么定
- 跑无延迟还是 LAN/WAN
- 用什么数据

### 第二步：优先复用现有组件

优先复用：

- 原 Kona 组件
- 现有批量乘法
- 现有批量转换
- 现有比较器
- 现有通信模式

### 第三步：实现完成后做堆糖检查

检查：

- 具体做了哪些协议层
- 有没有多算/少算一步
- B2A、swap、vote 有没有被偷偷放进别的模块

### 第四步：做不公平检查

检查：

- 功能边界
- 并行粒度
- 预处理口径
- 安全参数
- 运行资源
- 特殊优化

### 第五步：写 benchmark 前先声明统计口径

必须说明：

- `total_ms` 是什么
- `comm_ms` 是什么
- `compute_ms` 是什么
- `sent_bytes` 和 `rounds` 的来源
- 是否带 LAN/WAN

---

## 9. 当前项目里最危险的坑

当前项目最危险的，不是“某段代码是不是 AI 写的”，而是：

```text
实验口径差异可能被偷偷藏进实现里
```

这类问题的危险性高于很多小 bug，因为：

- 程序仍然会 PASS
- benchmark 仍然会出数字
- 甚至数字还会很好看

但实际上对照已经不公平了。

因此后续最重要的能力不是“重写某个协议”，而是：

```text
能不能快速识别：这次实验到底是不是同口径、同资源、同粒度、同功能边界。
```

---

## 10. 结论

以后每做一个新模块，都应该默认把下面三件事当成必做项：

1. 先问清楚模块边界和 benchmark 口径。
2. 做完后做堆糖检查。
3. 再做不公平检查。

如果这三件事没做，即使 benchmark 跑出来了，也不能默认相信结果。
