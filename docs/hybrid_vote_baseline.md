# 混合方案安全投票基准：算法、工程实现与通信推导

版本：`hybrid-vote-dcf-optimized-v1`。整理日期：2026-11-04。以本文件末尾记录的当前仓库源码为准。

本文件固定混合方案投票的输入输出、算法语义、优化分支和统计口径，供后续接入不同Top-k网络、比较实现及实验结果使用。它不修改协议，也不把旧实验改标为新实验。

## 1. 基准结论

当前混合方案调用 `KonaMaskVote::vote_dcf_optimized<64>()`：

1. 输入候选记录的秘密标签份额，以及表示是否进入Top-k的秘密mask。
2. 在公开类别域上，用批量DCF比较构造**类别累计票数**，本地作差得到各类别频数份额。
3. 用按层批量DCF的胜者树选最大频数；平票选**类别编码较小者**。
4. 只返回**获胜类别的加法秘密份额**，不返回公开标签或公开频数。
5. 公开Top-1、公开全部入选、单类别等情况走已有快捷分支。

这里的“类别累计计数”可记为CDF；DCF则是分布式比较函数比较器。两者不是同一个概念，也没有新增一个叫CDF的密码组件。

**本基准包含两个层次：投票功能和通信行为按真实实现执行；辅助秘密材料仍是现有L2性能测试设置，不宣称生产级隐私安全。**安全边界见第11节。

## 2. 实现边界与调用入口

| 职责 | 文件／接口 |
|---|---|
| 投票主入口 | `Machines/kona-mask-vote.hpp`：`vote_dcf_optimized()` |
| 类别累计计数 | 同文件：`label_counts_dcf_optimized()` |
| 只保留胜者的最大值选择 | 同文件：`winner_dcf_optimized()` |
| 投票统计 | 同文件：`DcfVoteStats` |
| 缓存批量DCF比较 | `Machines/kona-dcf-compare.hpp`：`Compare64::compare_in_vec()` |
| 批量乘法和公开常量份额 | `Machines/kona-share-conversion.hpp` |
| 当前独立消息并发收发 | `Networking/Player.h`：`exchange_concurrent()`；底层复用`Exchanger` |
| 混合方案实际接入 | `Machines/knn-bench.cpp`中的矩阵诊断、`hybrid_shared_engine`、`hybrid_full_engine` |

投票不需要知道Cong如何构造、矩阵如何剪裁或距离如何计算。候选满足接口契约即可调用。网络中的LAN/WAN比较器切换阈值，不作用于此投票：**本入口所有比较都是DCF**。

同文件仍保留旧的 `vote_with_dcf()`、PCR投票及原计数/最大值接口，用于历史对照；它们不是这里的优化基准。Shao现有投票也使用批量DCF，但调用的是旧计数/最大值接口，不能把它的通信公式直接套到本入口。原KONA按候选标签统计的投票也不是本入口。

## 3. 符号、输入与输出契约

| 符号 | 含义 |
|---|---|
| N | 原训练数据库条数，不一定等于投票候选数 |
| M | `candidates.size()`，实际传入投票的候选条数 |
| C | 公开类别数，标签编码必须在`0…C−1` |
| k | 调用方公开知道的实际入选数；不同于M |
| m_i | 候选i的秘密入选位，必须为0或1 |
| l_i | 候选i的秘密类别编码 |
| H | 比较及普通乘法的现有chunk上限：16,384项 |
| [x] | 在Z₂⁶⁴上的加法秘密份额，`[x]₀+[x]₁=x mod 2⁶⁴` |

候选采用现有二元记录格式：`candidates[i][0]`为距离份额，`[1]`为标签份额。投票只读取标签字段，不重新计算距离或Top-k。

### 3.1 两种mask表示

- **秘密mask模式**：`public_all_selected=false`，`mask.size()==M`。调用方保证mask是合法0/1份额；若声明公开k，还须保证`sum(mask)==k`。
- **公开全选模式**：`public_all_selected=true`，mask必须为空，且全部M条候选都已知入选。省略的是已经公开确定的mask运算，不能通过查看秘密份额猜测“全1”。

现有矩阵输出契约用空mask表示公开全选，因此bench可以根据该公开表示传参；不能把任意外部输入的空mask无条件视为合法全选。

`public_selected_count`是公开契约参数。默认0表示没有提供可用于Top-1优化的入选数量信息，**不是声明秘密mask之和为0**。当前混合bench传入公开k；模块不打开mask来验证这个承诺。

### 3.2 输出与边界行为

输出是一个`Z2<64>`赢家标签份额。另一方份额不在模块内重构；中间频数只以份额在内部保存。

- 平票：选最小类别编码。
- 单类别：返回类别0的份额，无通信。
- 空候选：返回类别0的份额。
- 全零mask且不错误声明Top-1：所有频数为0，按平票规则返回类别0。这是约定的退化输出，不代表找到了有效邻居。
- 非连续类别编码须由调用方另行定义编码和安全解码方式；不能把标签7直接作为`C=3`的合法输入。
- `winner_dcf_optimized()`要求初始标签字段就是公开类别索引。它不是任意秘密payload的通用argmax，不能直接换入其他标签。

当前实现检查类别数、向量长度、公开声明的部分一致性和比较索引溢出；不以安全协议证明秘密mask为bit或标签属于合法域。这些仍是调用方前置条件。

## 4. 普通分支的算法

### 4.1 计数：比较类别边界，累计后作差

定义：

\[
S=\sum_{i=0}^{M-1}m_i,\qquad
F_b=\sum_{i=0}^{M-1}m_i[l_i<b],\quad b=1,\ldots,C-1.
\]

所有`label<boundary`谓词按“边界×候选”展平成一个比较任务，共`M(C−1)`个谓词，交给批量DCF；超过H时按现有规则分chunk。

秘密mask模式再把比较结果与mask批量相乘。`S`直接对mask份额求和；公开全选时`S=M`，同时省去这些mask乘法。

设置`F₀=0，F_C=S`，各类别频数为：

\[
f_c=F_{c+1}-F_c,\quad c=0,\ldots,C-1.
\]

累计和及作差都是本地份额运算，无额外通信。该等价关系依赖标签是合法整数类别编码。

### 4.2 选胜者：C个类别上的锦标赛

初始结点为`([f_c],[c])`，按类别编码升序排列。每层把相邻结点配对，同层比较批量执行，奇数尾结点直接进入下一层。

每一对计算严格比较位：

\[
b=[f_L<f_R].
\]

随后只保留胜者所需的字段：

\[
[f_{win}]=[f_L]+[b]([f_R]-[f_L]),
\]

\[
[label_{win}]=[label_L]+[b]([label_R]-[label_L]).
\]

同层所有必要的秘密乘法合成批次。无需更新失败位置。

当两边频数相等，严格比较位为0，保留左边。每个子树对应连续、按序的类别区间，左子树的任何类别都小于右子树的类别，因此逐层保留左边实现全局最小类别平票规则。

### 4.3 选胜者的两个进一步节省

- **初始标签公开**：第一层可用`L+b(R−L)`本地计算胜者标签，秘密位乘公开常数不需要安全乘法。
- **最后一层只输出标签**：最终赢家频数没有后续用途，最后一层不计算它。

二分类尤其简单：比较两个频数后，赢家标签就是`[b]`，不需要额外赢家乘法。

## 5. 公开条件下的快捷分支

主入口先判断公开条件，再进入普通计数路径，顺序以源码为准：

| 条件 | 返回方式 | 比较／乘法 |
|---|---|---|
| C=1或M=0 | 类别0份额 | 无 |
| M=1且公开知道该条已入选 | 直接返回该标签份额 | 无 |
| 公开知道恰好选1条，但M>1 | `sum(mask[i] * label[i])` | M项批量乘法，无DCF |
| 普通秘密mask | 累计计数＋胜者树 | 正常比较及乘法 |
| 公开全选且非上述快捷分支 | 无mask乘法的累计计数＋胜者树 | 比较；必要的胜者乘法 |

**不能先秘密筛出k条、免费删掉其余候选，再当作公开全选。**安全压缩本身需要协议；这里仅利用上游已经提供的公开全选输出。

## 6. 明文案例：7个候选中选5个，3个类别

这是解释秘密运算语义的明文示意，真实调用中标签、mask和频数是份额。

| 候选 | A | B | C | D | E | F | G |
|---|---:|---:|---:|---:|---:|---:|---:|
| 标签 | 2 | 1 | 2 | 0 | 1 | 2 | 1 |
| 入选mask | 1 | 1 | 0 | 1 | 1 | 0 | 1 |

M=7、C=3、k=5，入选的是A、B、D、E、G。

- 边界1：累计`mask×[label<1]`，只有D贡献1，得到`F₁=1`。
- 边界2：B、D、E、G各贡献1，得到`F₂=4`。
- mask之和`S=5`。
- 三类频数：`f₀=1，f₁=4−1=3，f₂=5−4=1`。
- 胜者树先比较类别0与1：`1<3`，类别1获胜；类别2轮空。
- 最后一层比较频数3与1：保留类别1，只输出类别1的秘密份额。

例如赢家1可以表示为`[winner]₀=7，[winner]₁=2⁶⁴−6`；两方相加模2⁶⁴为1。该分解只是说明，不是实际固定输出。

平票示例：把G标签改为0，频数变为`(2,2,1)`，最终返回类别0。

Top-1示例：标签`(0,1)`、秘密mask`(0,1)`，公开k=1，直接计算`0×0+1×1=1`的份额。2项真实乘法，共32B/方、1次交换，不必再计数和选最大。

## 7. 通信与复杂度推导

以下都指**当前64位实现的每方应用payload发送量**，不含对方字节、长度帧头、TCP/IP头、ACK、离线密钥和材料、校验流量。

| 原语 | 每项每方发送 | 每方DCF evaluate调用 | 无跨chunk时交换次数 |
|---|---:|---:|---:|
| 一个DCF严格比较谓词 | 8B | 2次 | 整个批次1次 |
| 一个安全乘法项 | 16B | 0 | 整个批次1次 |
| 本地份额求和、相减、乘公开常数 | 0B | 0 | 0 |

一个比较谓词对应每方两次本地DCF评估，**不等于两个比较谓词或两轮通信**。

### 7.1 类别计数成本

令`A=M(C−1)`，且本节假定没有提前进入第5节的快捷分支：

- 秘密mask：比较A项，乘法A项；发送`24A B`；交换`2 ceil(A/H)`次。
- 公开全选：比较A项，无mask乘法；发送`8A B`；交换`ceil(A/H)`次。

统一规定`ceil(0/H)=0`。H表示chunk项数16,384；B仅用作字节单位。

### 7.2 胜者树成本：C≥2

比较谓词总数：

\[
P_w=C-1.
\]

必要的秘密乘法项总数：

\[
Q_w=2(C-1)-\lfloor C/2\rfloor-1
   =2C-3-\lfloor C/2\rfloor.
\]

解释：只计算胜者时，原本需要每对更新频数和标签，共`2(C−1)`项；第一层的`floor(C/2)`个公开标签选择不需要秘密乘法；最后一次赢家频数更新也省去1项。

因此赢家选择每方发送：

\[
D_w=8(C-1)+16Q_w\quad\text{字节}.
\]

准确轮次按每层计算。第l层从l=0开始：

\[
n_l=\lceil C/2^l\rceil,\quad p_l=\lfloor n_l/2\rfloor.
\]

该层乘法项数为：

\[
q_l=\mathbf1_{\text{非末层}}p_l+\mathbf1_{l\ge1}p_l.
\]

\[
R_w=\sum_l\left(\lceil p_l/H\rceil+\lceil q_l/H\rceil\right).
\]

没有跨chunk时，C=2为1次交换；C≥3为`2 ceil(log₂ C)`次交换。C=1由快捷分支处理。

### 7.3 普通投票总成本

秘密mask：

\[
P=M(C-1)+(C-1),\quad Q=M(C-1)+Q_w,
\]

\[
D=8P+16Q=24M(C-1)+8(C-1)+16Q_w,
\]

\[
R=2\lceil M(C-1)/H\rceil+R_w.
\]

公开全选：

\[
P=M(C-1)+(C-1),\quad Q=Q_w,
\]

\[
D=8M(C-1)+8(C-1)+16Q_w,
\]

\[
R=\lceil M(C-1)/H\rceil+R_w.
\]

每方DCF evaluate次数均为`2P`。Top-1加权分支另为：`P=0，Q=M，D=16M，R=ceil(M/H)`。公开唯一候选、单类别和空候选为0。

### 7.4 二分类直接公式

C=2时，`Q_w=0`，只有一个赢家DCF比较：

| 分支 | 每方发送字节 | 交换次数 |
|---|---:|---:|
| 普通秘密mask | `24M+8` | `2 ceil(M/H)+1` |
| 普通公开全选 | `8M+8` | `ceil(M/H)+1` |
| 公开k=1、M>1 | `16M` | `ceil(M/H)` |
| 已知唯一候选入选 | 0 | 0 |

普通两行须先排除快捷分支。

### 7.5 主案例与跨chunk案例

第6节M=7、C=3、k=5的秘密mask案例：

- 计数：14个谓词、14项乘法，发送`14×8+14×16=336B`，2次交换。
- 胜者树：2个谓词、2项乘法，发送`2×8+2×16=48B`，4次交换。
- 总计：**每方384B、6次交换、32次DCF evaluate**。

若上游已公开输出仅含那5条入选记录，则M=5、公开全选：计数80B，赢家48B，共**128B、5次交换**。这依赖不同的合法输入表示，不是秘密删除两条候选的免费操作。

跨chunk例：M=5,500、C=4、秘密mask、k不为1。计数A=16,500，比较和乘法各分2个chunk；赢家树4次交换。因此共8次交换、每方396,072B、33,006次DCF evaluate。不能仍写成“计数2轮、投票6轮”。

### 7.6 复杂度与耗时解释

普通分支谓词和乘法总量均为`O(MC+C)`，工作缓冲量为`O(MC+C)`；C固定较小时随候选M线性增长。赢家树比较数C−1、深度`ceil(log₂ C)`，不是候选之间的全对全比较。

M由上游输出决定，不等于N，也不必等于k。分块时通常由各块保留候选数累加，以实际`candidates.size()`为准；不取消分块时可能M>k，退化为单Cong后通常M=k且公开全选。投票时间和字节不能假定随k严格单调增长。

通信轮次也不能直接乘RTT作为时间结论。并发交换、TCP调度、payload大小、本地DCF和乘法计算都会影响在线时间，正式时间必须实测。

## 8. Arcene这批九个k的结构核对

原批次N=199、C=2，主块大小128。k≤20时为128+71分块，两个块均至少k条，所以M=2k；k≥40满足`4k>128`，取消外层分块，单Cong输出M=k，公开全选。

| k | M | 投票分支 | DCF谓词P | 乘法项Q | 每方DCF evaluate | 每方发送B | 交换次数 |
|---:|---:|---|---:|---:|---:|---:|---:|
| 1 | 2 | Top-1秘密mask加权 | 0 | 2 | 0 | 32 | 1 |
| 2 | 4 | 普通秘密mask | 5 | 4 | 10 | 104 | 3 |
| 5 | 10 | 普通秘密mask | 11 | 10 | 22 | 248 | 3 |
| 10 | 20 | 普通秘密mask | 21 | 20 | 42 | 488 | 3 |
| 20 | 40 | 普通秘密mask | 41 | 40 | 82 | 968 | 3 |
| 40 | 40 | 公开全选 | 41 | 0 | 82 | 328 | 2 |
| 60 | 60 | 公开全选 | 61 | 0 | 122 | 488 | 2 |
| 80 | 80 | 公开全选 | 81 | 0 | 162 | 648 | 2 |
| 100 | 100 | 公开全选 | 101 | 0 | 202 | 808 | 2 |

k=20到40，M仍是40，但不再需要40项mask乘法，所以968B/3次交换下降为328B/2次交换。这是公开输入分支变化，不是省略真实计算。

这些数字与原批次双方各三次日志逐项一致。该批次是WAN单程10ms、并发收发改造前的历史记录；本表用于核对字节和轮次，不把它改标为当前WAN单程20ms的时间基线。

## 9. 工程优化及固定规则

| 优化 | 固定的实现方式与边界 |
|---|---|
| 类别边界计数 | 原逐类双向相等比较的`2CM`谓词降为`(C−1)M`；mask乘法从CM降为`(C−1)M` |
| 跨类别合批 | 所有边界一次构造比较任务，不能按类别逐个发起交换；内部chunk仍真实执行 |
| 缓存DCF | 复用已构造的`Compare64`，密钥文件读取和缓存构造在投票计时前完成 |
| 公开全选 | 仅依据上游公开契约跳过mask乘法，不重构mask |
| 只更新胜者 | 不维护失败位置；初始公开标签本地选择，末层不再计算频数 |
| Top-1快捷分支 | 利用公开k=1，做真实mask×标签批量乘法；不先公开寻找入选位置 |
| chunk | 维持16,384上限，比较和乘法分别统计实际chunk |
| 并发收发 | 双方独立消息已就绪时使用`exchange_concurrent()`；不改变字段、payload、chunk和依赖关系 |
| 输出 | 主入口仅返回赢家标签份额，调试重构移到计时外 |

并发工程版本为`framed-full-duplex-v1`，复用已有非阻塞Exchanger，不新建收发线程。每次交换仍有两个真实方向操作、一次逻辑交换；单方发送量不乘二，重叠通信耗时只计一次。

它不把不同轮次的依赖计算变成同时执行，也不保证所有小消息或计算阶段都达到峰值带宽。旧比较器、原KONA控制路径和Shao旧投票不能在没有说明的情况下重标为本优化入口。

## 10. 后续接入与实验口径

推荐直接调用现有C++模块，不在Python组织脚本或bench里复制投票算法：

```cpp
KonaMaskVote::DcfVoteStats shape;
Z2<64> winner_share = KonaMaskVote::vote_dcf_optimized<64>(
    output.candidates,
    output.mask,
    public_class_count,
    player,
    dcf,
    public_all_selected,  // 来自上游公开协议契约
    &shape,
    public_k);
```

投票计时范围：调用开始到赢家份额返回，包含函数内部的索引/缓冲构造、本地累计及选择运算。候选/测试份额准备、DCF缓存初始化、同步、日志和校验重构在外。不能把函数内部现有工作悄悄移出计时却继续当作同一基准。

每次必须记录M、C、公开k、mask表示、投票后端、chunk、分支标记，以及双方时间/字节/计数。关键自检：

```text
P = shape.count_predicates + shape.winner_predicates
Q = shape.mul_items
每方发送payload字节 = 8*P + 16*Q
每方DCF evaluate调用增量 = 2*P
交换次数 = shape.compare_chunks + shape.mul_chunks
原始方向操作数 = 2*交换次数
```

`direct_label`表示直接返回唯一候选标签的分支；`single_selected`表示Top-1加权求和分支，二者不是同一个标记。

时间取每次双方较大值；重复实验报告均值及样本标准差。完整在线与各阶段分别记录，涉及阶段拼接时先按同方合计，再取双方较大值，并明确标为合成；历史数据沿用当时口径，不能悄悄重算改标。

当前WAN固定每路40Mbps、额外单程20ms；历史10ms记录单独标注。时间横向比较要求同构建、同网络、同CPU映射及交替执行；字节/轮次一致不能保证耗时必然一致。以后更换材料、安全级别、chunk、类别编码、快捷分支或比较器，都需要显式区分基准版本。

## 11. 安全与完整性边界

算法层面，中间标签、mask、频数和比较位都按份额处理，主入口不要求公开重构这些值；验证bench只在计时结束后重构检查。

**但当前工程不是生产安全实现。**现有L2乘法使用`a=b=c=0`，交换`x−a`和`y−b`后可重构乘法输入，因而不能据“没有显式reveal函数”声称这些秘密没有泄漏。DCF也沿用仓库测试材料和复用设置，本基准不为其生产安全作保证。

因此本基准可用于功能、协议形状、真实通信payload和在线性能测试；不能单凭输出是秘密份额就宣称端到端隐私已经实现。升级生产安全须另行提供合适的新鲜相关材料、满足使用约束的DCF/FSS材料、输入有效性与威胁模型分析，并重新核验性能口径。

当前快捷分支只使用公开条件，保持原赢家语义；不允许为了测性能把真实计数、比较或乘法换成明文答案后只补发等长消息。
