## 4. 在线区间与结束条件

测量范围内实际需要的操作必须计入：

- 秘密比较、DCF/PCR等后端evaluation、必要的份额转换。

- rank累计、rank-mask计算。
- packing/unpacking、chunk处理、全部通信与等待。
- 对应范围内的其他在线本地计算。

结束条件是该范围约定的输出份额已经准备好。时间与通信快照使用同一协议边界：

```text
输入、材料、公开计划与缓冲区准备完成
→ 双方计时外同步
→ 获取通信起始快照，开始在线计时
→ 执行所选范围内全部在线操作
→ 输出份额就绪，停止计时，获取通信结束快照
→ correctness reveal、明文验证、checksum、日志和结果写入
```

`comm_ms`表示通信API累计时间；`online_ms - comm_ms`只能解释为非通信API剩余时间，不能称为纯密码计算时间。compare＋swap的阶段时间不得标成compare-only。

## 5. 双方原始数据与主指标

每个trial先分别记录两方数据，再产生该trial的汇总值。

| 指标 | 原始记录 | 正式汇总值 |
|---|---|---|
| 在线墙钟时间 | P0_time、P1_time | max(P0_time, P1_time) |
| 发送字节 | P0_sent_bytes、P1_sent_bytes | max(P0_sent_bytes, P1_sent_bytes) |
| 底层通信动作数 | P0、P1各自记录 | 两方分别展示 |
| 实际完整交换次数 | P0、P1各自记录 | 两方分别展示 |

```text
trial_time  = max(P0_time, P1_time)
trial_bytes = max(P0_sent_bytes, P1_sent_bytes)
```

通信量取较大一方的发送量，不是双向总量，不乘二。较慢的一方与发送量较大的一方可能不同，不要求来自同一party。

各方发送字节使用在线区间前后累计发送量的差值，统计实际应用协议payload；不含TCP/IP头、ACK、重传，也不包含区间外的同步、初始化和reveal。

## 6. 通信轮数命名

| 字段 | 含义 |
|---|---|
| transport_rounds | 本方底层send/receive动作总数；一次send加一次receive计2 |
| exchange_rounds | 实际完整双方交换次数，包含顺序chunk引入的额外交互 |
| structural_depth | 网络比较层深度，不是通信轮数 |
| theoretical_rounds（可选） | 不拆chunk的理论依赖交互数，独立记录 |

P0/P1的transport_rounds和exchange_rounds都要保留，不能只输出其中一方或用一个max掩盖差异。

只有确认全部通信均为成对send/receive时，才可使用：

```text
exchange_rounds = transport_rounds / 2
```

一次API可能已完成双向交换，必须按其实际语义计数。TCP分包不算额外协议轮次，比较器数量也不能代替通信轮数。

旧字段logical_rounds在不同bench中存在不同含义。迁移时明确映射实际exchange或理论交互，不能只凭字段名拼表。适用时保留按后端阶段/chunk推导与实际通信计数的交叉校验。

## 7. 重复实验、阶段归因与汇总

- 每个trial先取两方时间max、发送量max，再对trial值统计；不能以各方均值的max代替逐trial的max。
- 报告实际样本数、mean、median、sample SD、CV、min、max。只有一个样本时，样本SD和CV记为不适用，不伪造为0。
- 保存P0/P1原始值、各trial汇总值与实际执行顺序。
- 预热单独标记，不进入正式统计；保留慢trial，不只报告最好值。
- 对照实验使用同构建、同输入规则、同网络和CPU条件，串行运行进程对，采用交错或AB/BA轮换。
- 阶段数据分别保留双方。解释某个trial的总耗时时，使用该trial总时间较长一方的阶段数据，不能把各阶段跨方max拼成一个总时间。
- 各阶段时间max之和，不保证等于完整流程时间max；各阶段发送量max之和，也不保证等于完整流程发送量max。闭合检查应先在每一方自己的统计中进行。
- 明确记录阶段之间的在线收集、重排等成本；阶段表未覆盖的在线间隙不能静默丢弃。
- 结构、后端、字节和通信轮数不变时，不凭跨批少量时差归因于算法。回归先检查阶段，不先修改阈值。

## 9. 完整KNN在线端到端与各阶段必须同时记录

完整KNN实验必须在**同一次trial、同一次真实连续执行**中，从开始在线距离计算到最终获胜类别秘密份额就绪，独立测量外层`knn_online_e2e_ms`以及完整在线发送字节、通信动作数和交换次数。总时间不能用阶段时间相加代替，也不能把各阶段分别重跑的结果拼成一次完整KNN。最终无需输出具体频数；正确性检查所需的reveal在结束快照之后执行。

必须分别保存下列在线阶段的数据：

| 阶段 | 边界 | 每方必须保留 |
|---|---|---|
| Distance | 输入份额就绪至距离份额就绪 | online_ms、sent_bytes、transport_rounds、exchange_rounds（适用时） |
| Top-k | 距离/标签份额就绪至约定Top-k输出份额就绪 | 同上 |
| 安全投票 | Top-k标签或候选＋成员mask份额就绪至获胜类别秘密份额就绪 | 同上 |
| 在线衔接/其他 | 未被以上阶段覆盖的必要转换、收集、重排及在线间隙 | 同上；时间可含轻量插桩开销 |
| 完整KNN在线总量 | 完整在线起点至最终类别秘密份额就绪 | 独立外层墙钟时间及起止通信计数差值 |

各阶段内继续保留适用的细分数据，例如分块Cong、候选收集、矩阵末端、比较器、swap；计时和通信数据都要有。父阶段与子阶段明确层级，DCF evaluation属于比较阶段子项，不重复加到总量。未执行或不在测量范围内的阶段标为`NOT_IN_SCOPE`，不能伪造为0；实际执行但没有通信的阶段发送字节和动作数则如实记0。

这里只要求**在线性能数据**。读取、离线材料准备、连接初始化等即使额外记录，也必须放在单独的准备信息中，不能加入在线阶段表或完整在线总量。Top-k-only只报告`topk_online_ms`等阶段指标；它的独立外层计时仍是Top-k阶段时间，不称为端到端。

为减少干扰，在线执行中只采集必要的单调时钟时间戳及累计发送字节/通信动作计数快照，写入预先分配的记录缓冲。阶段差分、轮次推导、跨方统计交换、max与均值汇总、断言校验、格式化和日志写入均放在完整在线结束快照之后。**不能把阶段边界快照也延后到结束后才采集**，否则无法还原各阶段实际耗时和通信。不得为统计增加阶段间网络barrier；协议本身必须的同步和等待保留在在线范围内。

先在每方内部检查闭合：互不重叠的阶段发送字节/动作数之和等于完整在线差值；外层时间减去互不重叠的阶段时间，记录为`online_other_ms`，不静默丢弃。顺序执行且各阶段完整交换定义一致时，检查阶段交换次数之和；单向通信或交换跨越阶段边界时记录实际动作和归属规则，不能直接除以二。若存在并行或重叠阶段，标明重叠关系，不能强求时间相加；每次发送和通信动作只归属一个叶子阶段。

完整在线总量和每个阶段都按第5节处理：逐trial时间取双方max、发送字节取双方max，P0/P1的动作数与交换次数分别保存。各阶段max之和不等于完整总量max，归因与闭合按第7节执行。插桩仍有开销，须注明统计方式，不能将细小耗时差解释成算法改进。

每份原始日志须自行携带环境头和状态，不依赖文件名才能解释：时间/run、命令、数据集和规模、party/trial、测量与输出范围、backend/material模式、网络profile及实际qdisc/class/filter与offload状态、实际CPU affinity、源码/二进制指纹、开始/结束/退出码。区分`COMPLETED`（执行完成）、`accounting_check=PASS`（统计校验通过）和`correctness=NOT_CHECKED/PASS/FAIL`（结果验证）；不得用前两者替代第三者。失败日志也要保留。环境采集失败标为未知或失败，不能推断为无延迟。

## 13. 调度脚本、不同物理核心与核心独占的正式标准

2026-11-04确认：**P0与P1必须分属两个不同物理核心；每个被分配的物理核心只运行对应的一个协议进程及其所属线程。固定绑核和核心独占同时成立，才满足正式单核对比条件。**

同日最终确认：**所有本项目实验固定P0→逻辑CPU 0、P1→逻辑CPU 2，不随方案、数据集、网络或trial改变。若0/2不可用或不满足不同物理核心条件，应报错并解决环境，不自动挑选其他CPU。** 单进程离线/结构实验固定CPU 0，CPU 2不另起无意义进程。

### C++与脚本的责任边界

| 层次 | 必须负责的内容 |
|---|---|
| C++协议模块 | 执行真实算法、比较器、交换、通信及安全投票 |
| C++ bench | 一次trial内部的协议流程；在线起止边界；完整KNN及各阶段的时间/字节/通信动作快照；在线结束后的正确性检查 |
| Python / Shell调度脚本 | 双方启动和退出管理；输入/参数；统一CPU映射与隔离配置的组织/核验；实际网络配置；全局交替顺序；原始日志、逐trial双方汇总和统计；最终清理 |

**实现位置按用户最终偏好统一：保留已有位置，新增或后续修改的实验优先在C++ bench内绑定。** 已有C++绑定就修改C++，已有Shell/Python绑定就修改脚本，不为统一而搬迁已经工作的绑定。没有绑定的独立bench本次补C++绑定。以后新增/修改实验，首先使用`Machines/kona-bench-affinity.hpp`在参数解析后、网络/工作线程创建和在线计时前绑定；bench确实无法控制时才由脚本或启动命令taskset兜底，并记录原因。CPU分配标准始终是0/2。

脚本发出的taskset约束被启动的协议进程及其继承的线程，不代表把Python调度进程本身绑到该核心。C++共用入口发现继承的单CPU affinity已经正确时只核验，不重复改绑；发现目标固定CPU被父级affinity/cpuset排除时直接失败，不覆盖冲突、不自动换核。若脚本和C++都参与，必须使用同一固定映射，并在计时前记录实际生效结果。

共用入口输出`BENCH_AFFINITY`，包括party/CPU、设置来源、实际绑定检查、可见socket/core/SMT同胞以及独占核验状态。C++或脚本都不能仅凭一次绑核宣称核心独占：排他隔离仍需操作系统/宿主环境落实。迁移清单与验证见[bench_cpu_affinity.md](bench_cpu_affinity.md)。

脚本启动、构建、环境配置、元数据查询、结果汇总和日志写入不计入协议在线性能。在线区间内实际发生的通信、等待、本地计算及必要采样开销仍由C++外层计时覆盖，不能因为由脚本组织实验就扣除。脚本本身不实现协议，也不能替代C++端到端/阶段快照；更换启动方式不得悄悄改变测量边界。

### 两个不同物理核心，各专供一个进程

1. 每次trial只启动一对协议进程：P0一个、P1一个，固定使用CPU 0和CPU 2作为执行位置；两个逻辑CPU必须对应**不同的物理核心**，仅CPU编号不同不够。
2. 实验前记录CPU拓扑：CPU型号、逻辑CPU编号、socket/core编号、SMT同胞列表、NUMA关系、实际可用cpuset和CPU quota。跨方案与跨trial保持P0/P1到核心的映射不变，不临时换核挑选结果。
3. **整个物理核心必须独占。** 所选执行CPU不能运行其他用户进程；同一物理核心的其他SMT线程也必须预留为空闲或离线，不能分给P1、其他实验、Python调度、日志进程或后台任务。双方不能共用一个物理核心的两个SMT线程。
4. 使用能排除其他进程的核心隔离/独占cpuset等配置，并让其他用户任务、构建、调度、日志与监控在其他核心运行。`taskset`只限制目标进程可以去哪里，**并不阻止其他进程进入该核心，因此单独使用taskset不满足本条。** 仅创建cpuset但仍允许其他任务使用相同CPU，同样不满足独占要求。
5. 记录并核实协议进程及其全部线程的实际affinity。默认比较口径是每方使用一个物理核心上的一个逻辑CPU；后端的辅助线程也必须服从该限制，不得悄悄利用额外核心。多核/多进程变体需单独命名、单独报告，不能混入此单核口径。
6. 采集隔离配置、SMT预留状态和测量窗口内调度/负载证据。单次`ps`未看到其他任务只能作为抽样记录，不能证明整个实验期间核心独占。系统中断、内核活动及虚拟化宿主竞争的控制范围和残余活动需如实记录，不把“未检查”写成“无干扰”。
7. Docker内可见CPU编号或WSL虚拟CPU拓扑，不能自动证明宿主物理核心已独占。若容器/虚拟化环境无法核实不同物理核心或排除宿主其他任务，则记录实际隔离范围，**不能标注为满足本节严格核心独占标准**；先解决隔离条件，再执行满足该标准的正式对比。

### 固定条件与交替执行

- 同一批使用同一源码/构建、相同输入划分和查询、k、材料模式、chunk策略、CPU映射和线程配置。仅改变被比较的方案或明确声明的网络条件。
- 每次只运行一个协议进程对；不得同时运行另一套bench、网络吞吐测试或后台协议负载。上一trial退出并完成计时外日志保存后，再启动下一trial。
- 不先连续跑完一个方案/条件的所有重复。两条件使用`A1 → B1 → A2 → B2 → A3 → B3`；多个方案/数据集按轮次循环。需要AB/BA平衡时，在运行前固定并记录计划，不依据已观察到的耗时临时调整。
- 保存计划和实际顺序、预热策略、每trial起止与双方退出状态。失败/超时保留原始记录；重试另编号并说明，不覆盖、不静默替换慢trial。
- 网络profile标签、CPU参数和脚本名都不能代替实际环境证据。记录qdisc/class/filter、offload和运行前后状态；同一profile除明确对比项外保持其余条件一致。

### 汇总与合规状态

每个trial、每个阶段以及完整在线总量均保留双方原始值：时间取`max(P0_time,P1_time)`，发送字节取`max(P0_sent_bytes,P1_sent_bytes)`，实际通信动作数和交换次数分别保存P0/P1。先逐trial取max，再统计mean/median/sample SD/CV/min/max；不相加双方字节、不把理论轮次替代实际交换，也不拼接各阶段max来伪造完整总量。

运行记录应分别写明`affinity_check`、`physical_core_separation`和`core_exclusivity`等环境核验状态，并注明证据位置。任一硬条件缺失、失败或未核实，就不能把该运行标为满足本节正式对比条件；已有原始结果照常保留并标注环境限制，不能事后补写独占声明。
