## 1. 这个模块在比较协议里的位置

比较协议大概是：
$$
x-y \quad \Longrightarrow \quad e
$$
然后前置处理把 $e$ 拆成两个随机掩蔽数：
$$
e = u+v \pmod {2^{64}}
$$
接着把 $u,v$ 变成二进制共享：
$$
[[u]] \Rightarrow [[\bar u]],\qquad [[v]] \Rightarrow [[\bar v]]
$$
bitwise adder 做的就是：
$$
[[\bar s]] = [[\bar u]] + [[\bar v]]
$$
输出：
$$
s^{(0)},s^{(1)},\dots,s^{(63)},s^{(64)}
$$
其中：
$$
s^{(64)}=c^{(64)}
$$
这个最高 carry 就是你后面比较判断要用的东西。DOPM 原文也是这个逻辑：bitwise sum 负责并行计算 carry，最高位决定 $x\ge y$ 还是 $x。

## 2. 输入输出规格，按你现在 64 位版本定

### 输入

暂定输入两个 64-bit 的 Boolean/XOR 共享值：
$$
[[u]], [[v]]
$$
每个值由两台服务器各持有一份：
$$
[[u]] = u_0 \oplus u_1
$$
实现里可以直接用 `uint64` 存整个位串：

```
u_share = (u0_uint64, u1_uint64)
v_share = (v0_uint64, v1_uint64)
```

每个 bit 的语义是：

```
u_i = bit(u0, i) XOR bit(u1, i)
v_i = bit(v0, i) XOR bit(v1, i)
```

位序建议固定为：

```
bit 0 = 最低位 LSB
bit 63 = 最高位 MSB
```

不要反过来。不然后面 carry 会全乱。

### 输出

输出建议分两部分：

```
sum_low64_share: XOR-share 的 uint64
carry_out_share: XOR-share 的 1-bit
```

数学上等价于：
$$
u+v = s_{\text{low64}} + 2^{64}\cdot c_{64}
$$
也就是：

```
sum_low64 = (u + v) mod 2^64
carry_out = floor((u + v) / 2^64)
```

如果只是比较模块，有时候你只需要 `carry_out_share`，但我建议 Codex 仍然把 `sum_low64_share` 和 `carry_out_share` 都返回，方便测试。

## 3. 边界条件

你现在说“真实数字和份额都控制在 64 位里面”，那么这个模块的边界要这么定：

### 边界 1：输入必须是 64-bit

也就是：

```
0 <= u < 2^64
0 <= v < 2^64
```

每个 share 也必须 mask 到 64 位：

```
MASK64 = (1 << 64) - 1
u0 &= MASK64
u1 &= MASK64
v0 &= MASK64
v1 &= MASK64
```

### 边界 2：输出是 65-bit

因为两个 64-bit 数相加，最大是：
$$
(2^{64}-1)+(2^{64}-1)=2^{65}-2
$$
所以结果最多需要 65 位。低 64 位放在 `sum_low64`，最高第 64 位放在 `carry_out`。

### 边界 3：`c[0] = 0`

最低位没有输入进位：
$$
c^{(0)} = 0
$$
所以：
$$
s^{(0)} = u^{(0)} \oplus v^{(0)}
$$

### 边界 4：最高输出位不是 `sum_low64` 的 bit63

这个特别容易写错。

最终判断用的是：
$$
s^{(64)}=c^{(64)}
$$
不是：
$$
s^{(63)}
$$
也就是说，64-bit 加法的最终溢出位，是一个额外 bit。

### 边界 5：如果做比较，要保证比较语义和补码/模语义一致

bitwise adder 本身只负责算：
$$
u+v
$$
它不负责判断你这个 $u+v$ 到底代表有符号数还是无符号数。

如果你用它做 DOPM 风格比较，那么前面的 $u,v$ 拆分必须保证：
$$
u+v \equiv x-y \pmod {2^{64}}
$$
并且你后面解释最高 carry 的方式要固定。DOPM 里用最高位判断 $x-y$ 的符号：最高位为 0 时认为 $x\ge y$，最高位为 1 时认为 $x。

## 4. 前置处理

### 4.1 从算术份额到 bitwise 输入

如果你现在有差值的算术份额：
$$
[[e]] = e_0 + e_1 \pmod {2^{64}}
$$
可以做随机拆分：
$$

## 5. 并行进位核心公式

对每一位 $i$：

### propagate

$$
p_i = u_i \oplus v_i
$$

意思是：如果低位传来 carry，那么这一位会不会把 carry 继续传上去。

### generate

$$
g_i = u_i \land v_i
$$

意思是：这一位自己会不会产生 carry。

### carry 递推

普通串行写法是：
$$
c_0 = 0
$$
但是这个是 ripple-carry，会一位一位传，太慢。

并行前缀写法把每一位看成一个 pair：
$$
(G_i,P_i)=(g_i,p_i)
$$
合并两个相邻区间时：
$$
P_{\text{new}} = P_{\text{high}} \land P_{\text{low}}
$$
这个意思是：

如果高区间自己产生 carry，那么整个区间产生 carry；否则，如果高区间全传播，并且低区间产生 carry，那么整个区间也产生 carry。

最终每个位置会得到：
$$
G_i = c_{i+1}
$$
也就是第 $i$ 位算完之后传给下一位的 carry。

## 6. 推荐给 Codex 的伪代码

这是最适合你现在实现的版本：**64-bit Kogge-Stone / parallel-prefix carry adder**。它不是串行进位，固定 6 层就能处理 64 位。

```
function BITWISE_ADD_64(u_share, v_share):

    # 输入：
    #   u_share: XOR-share uint64, represents u
    #   v_share: XOR-share uint64, represents v
    #
    # 输出：
    #   sum_share: XOR-share uint64, represents (u + v) mod 2^64
    #   carry64_share: XOR-share bit, represents carry out bit

    MASK64 = 2^64 - 1

    # 1. 每一位的 propagate
    P = u_share XOR v_share

    # 2. 每一位的 generate
    G = SECURE_AND(u_share, v_share)

    # 3. 并行前缀传播
    # offset = 1,2,4,8,16,32
    for offset in [1, 2, 4, 8, 16, 32]:

        # 注意：这里要使用旧的 P 和 G 计算新的 P 和 G
        oldP = P
        oldG = G

        # 对每个 i >= offset:
        #   G[i] = oldG[i] OR (oldP[i] AND oldG[i-offset])
        #   P[i] = oldP[i] AND oldP[i-offset]
        #
        # bitset 版本可以用 shift 实现：
        shiftedG = oldG << offset
        shiftedP = oldP << offset

        shiftedG = shiftedG & MASK64
        shiftedP = shiftedP & MASK64

        candidate = SECURE_AND(oldP, shiftedG)

        # 理论公式是 OR
        # 稳妥实现：
        G = SECURE_OR(oldG, candidate)

        P = SECURE_AND(oldP, shiftedP)

    # 4. 此时 G 的第 i 位就是 c[i+1]
    # carry into bit i 等于 G[i-1]
    carry_into_low64 = (G << 1) & MASK64

    # 5. sum bit
    # s[i] = p[i] XOR c[i]
    sum_share = (u_share XOR v_share) XOR carry_into_low64

    # 6. 最高 carry
    carry64_share = bit(G, 63)

    return sum_share, carry64_share
```

注意，这里伪代码里的 `<<`、`& MASK64`、`bit(G,63)` 对 XOR-share 也可以逐份额本地做：

```
shift_share((a0,a1), offset) = ((a0 << offset) & MASK64, (a1 << offset) & MASK64)
bit_share((a0,a1), i) = ((a0 >> i) & 1, (a1 >> i) & 1)
```

## 7. 关键实现提醒

### 第一，循环里必须用 oldP / oldG

不能边更新边用新值，否则 prefix 会乱。

错误写法：

```
G = secure_or(G, secure_and(P, G << offset))
P = secure_and(P, P << offset)
```

正确写法：

```
oldG = G
oldP = P
G = secure_or(oldG, secure_and(oldP, oldG << offset))
P = secure_and(oldP, oldP << offset)
```

### 第二，shift 后必须 mask 到 64 位

Python 整数不会自然溢出，所以必须：

```
x = x & MASK64
```

否则高位会污染结果。

### 第三，sum 用的是原始 propagate

理论上：
$$
s_i=p_i\oplus c_i
$$
这里的 $p_i$ 是最开始的：
$$
p_i=u_i\oplus v_i
$$
不是 prefix 循环之后被更新过的 $P_i$。

所以实现里要保存：

```
P0 = xor_share(u_share, v_share)
```

最后：

```
sum_share = xor_share(P0, carry_into_low64)
```

不要用循环后的 `P` 来算 sum。

好，我们把**并行进位加法器**当成一节课来讲。你先把它从“加法器”里拆出来看：它真正要解决的不是“怎么异或出 sum”，而是**怎么快速知道每一位的进位 carry**。

普通加法里，最麻烦的是 carry。因为第 10 位有没有进位，可能取决于第 9 位；第 9 位又取决于第 8 位；一直传到最低位。这就是串行 ripple-carry。并行进位加法器的核心思想就是：**不要一位一位等进位，而是把“某一段 bit 会不会产生进位、会不会传播进位”提前合并出来。**

# 1. 先从普通二进制加法开始

假设我们要算两个二进制数：
$$
u+v
$$
每一位是：
$$
u_i,\ v_i
$$
其中 $i=0$ 是最低位。

普通加法每一位满足：
$$
s_i = u_i \oplus v_i \oplus c_i
$$
其中：
$$
c_i
$$
表示进入第 $i$ 位的进位。

最低位没有外来进位，所以：
$$
c_0 = 0
$$
然后第 $i$ 位会产生给下一位的进位：
$$
c_{i+1}
$$
普通全加器公式是：
$$
c_{i+1} = (u_i \land v_i) \lor ((u_i \oplus v_i)\land c_i)
$$
这条公式非常重要。

它的意思是：

第一种情况，当前位自己就能产生进位：
$$
u_i=1,\ v_i=1
$$
那么不管 $c_i$ 是什么，下一位都有进位。

第二种情况，当前位不能自己产生进位，但是可以传播低位传来的进位：
$$
u_i \oplus v_i = 1
$$
也就是当前位一个是 0，一个是 1。此时如果 $c_i=1$，那么也会把进位传到下一位。

------

# 2. generate 和 propagate 是核心

为了把上面的公式抽象出来，定义两个东西。

## generate：当前位自己产生进位

$$
g_i = u_i \land v_i
$$

它表示：

> 第 $i$ 位自己能不能产生一个 carry。

如果：
$$
u_i=1,\ v_i=1
$$
那么：
$$
g_i=1
$$
说明这一位一定向高位产生进位。

## propagate：当前位是否传播进位

$$
p_i = u_i \oplus v_i
$$

它表示：

> 如果低位传来 carry，第 $i$ 位会不会把它继续传上去。

如果：
$$
u_i=0,\ v_i=1
$$
或者：
$$
u_i=1,\ v_i=0
$$
那么：
$$
p_i=1
$$
说明这一位会传播 carry。

于是 carry 递推公式变成：
$$
c_{i+1}=g_i \lor (p_i \land c_i)
$$
这就是并行进位加法器的基础。

# 3. 为什么普通递推慢？

如果你直接算：
$$
c_1 = g_0 \lor (p_0 \land c_0)
$$
一直算到：
$$
c_{64}
$$
那就是串行的。

因为 $c_{64}$ 依赖 $c_{63}$，$c_{63}$ 依赖 $c_{62}$，一路依赖到 $c_0$。

这就是 ripple-carry：

```
c0 -> c1 -> c2 -> c3 -> ... -> c64
```

如果在安全计算里，每一层 AND/OR 都可能涉及交互，那这个串行链条就很难受。

并行进位加法器要做的是：

```
第 1 轮：每 1 位合并成 2 位信息
第 2 轮：每 2 位合并成 4 位信息
第 3 轮：每 4 位合并成 8 位信息
第 4 轮：每 8 位合并成 16 位信息
第 5 轮：每 16 位合并成 32 位信息
第 6 轮：每 32 位合并成 64 位信息
```

所以 64 位只需要：
$$
\log_2 64 = 6
$$
轮传播。

这就是“并行进位”的核心收益。

# 4. 从单个位扩展到“一段 bit”

单个位有：
$$
(g_i,p_i)
$$
现在我们不只看某一位，而是看一段区间。

比如区间：
$$
[0,3]
$$
也就是第 0、1、2、3 位。

我们希望知道两件事：

第一，这一整段会不会**自己产生一个 carry**，传给第 4 位？

第二，如果第 0 位之前有一个外来 carry，这一整段会不会把它一路传播到第 4 位？

所以对一个区间，也定义：
$$
G_{j:i}
$$
表示从第 $i$ 位到第 $j$ 位这个区间整体是否产生 carry。
$$
P_{j:i}
$$
表示从第 $i$ 位到第 $j$ 位这个区间整体是否传播 carry。

注意：
$$
j
$$
是高位，
$$
i
$$
是低位。

# 5. 区间合并公式

假设我们有两个相邻区间：

低区间：
$$
[i,k]
$$
高区间：
$$
[k+1,j]
$$
现在要合并成：
$$
[i,j]
$$
低区间的信息是：
$$
(G_{\text{low}},P_{\text{low}})
$$
高区间的信息是：
$$
(G_{\text{high}},P_{\text{high}})
$$
那么合并后的 propagate 是：
$$
P_{\text{new}} = P_{\text{high}} \land P_{\text{low}}
$$
意思是：

> 整个大区间能传播 carry，当且仅当高区间能传播，低区间也能传播。

因为 carry 要从最右边一路穿过整个区间，任何一段不传播，它就断了。

合并后的 generate 是：
$$
G_{\text{new}}
=
G_{\text{high}}
\lor
(P_{\text{high}}\land G_{\text{low}})
$$
意思是：

> 大区间产生 carry，有两种情况。

第一，高区间自己就产生 carry：
$$
G_{\text{high}}=1
$$
第二，低区间产生 carry，而且高区间愿意把它继续传出去：
$$
G_{\text{low}}=1,\quad P_{\text{high}}=1
$$
所以：
$$
G_{\text{new}}
=
G_{\text{high}}
\lor
(P_{\text{high}}\land G_{\text{low}})
$$
这就是并行进位加法器最核心的公式。

------

# 6. 为什么这个公式可以并行？

因为每一轮只合并固定距离的前缀。

以 8-bit 为例，初始每一位有自己的：
$$
(G_i,P_i)=(g_i,p_i)
$$
也就是每一位只知道自己这一位的情况。

## 第 1 轮：offset = 1

每一位 $i$ 和它左边距离 1 的低位 $i-1$ 合并。

也就是：
$$
(G_i,P_i)
$$
吸收：
$$
(G_{i-1},P_{i-1})
$$
更新后，第 $i$ 位知道的是：
$$
[i-1,i]
$$
这两位整体的 generate / propagate。

比如：

```
bit1 知道 bit0~bit1 的情况
bit2 知道 bit1~bit2 的情况
bit3 知道 bit2~bit3 的情况
...
```

## 第 2 轮：offset = 2

现在每一位已经知道自己往低位 2 位范围的信息。

再合并距离 2 的区间。

更新后，第 $i$ 位知道的是：
$$
[i-3,i]
$$
也就是 4 位范围。

比如：

```
bit3 知道 bit0~bit3 的情况
bit4 知道 bit1~bit4 的情况
bit5 知道 bit2~bit5 的情况
...
```

## 第 3 轮：offset = 4

再合并距离 4 的区间。

更新后，第 $i$ 位知道的是最多 8 位范围。

比如：

```
bit7 知道 bit0~bit7 的情况
```

所以 8-bit 只需要 offset：

```
1, 2, 4
```

64-bit 需要：

```
1, 2, 4, 8, 16, 32
```

------

# 7. 这个 G 最后到底是什么？

这是最重要的理解点。

初始：
$$
G_i = g_i
$$
只表示第 $i$ 位自己会不会产生进位。

经过并行前缀合并之后：
$$
G_i
$$
变成：
$$
G_{i:0}
$$
也就是第 0 位到第 $i$ 位这一整段，会不会产生一个 carry 传给第 $i+1$ 位。

而这个东西正好就是：
$$
c_{i+1}
$$
因为：
$$
c_0 = 0
$$
所以从第 0 位到第 $i$ 位整体产生的 carry，就是进入第 $i+1$ 位的进位。

因此最终有：
$$
G_0 = c_1
$$
一直到：
$$
G_{63}=c_{64}
$$
所以：

```
G 的 bit0 = c1
G 的 bit1 = c2
G 的 bit2 = c3
...
G 的 bit63 = c64
```

最终最高进位就是：

```
carry64 = G[63]
```

# 8. sum 怎么算？

sum 的公式仍然是：
$$
s_i = u_i \oplus v_i \oplus c_i
$$
而：
$$
p_i = u_i \oplus v_i
$$
所以：
$$
s_i = p_i \oplus c_i
$$
现在我们已经知道：

```
G[0] = c1
G[1] = c2
G[2] = c3
...
```

那进入每一位的 carry 是：

```
c0 = 0
c1 = G[0]
c2 = G[1]
c3 = G[2]
...
c63 = G[62]
```

所以可以把 G 左移一位：

```
carry_into_bits = G << 1
```

这会得到：

```
bit0 = 0
bit1 = c1
bit2 = c2
bit3 = c3
...
bit63 = c63
```

然后：

```
sum_low64 = P0 XOR carry_into_bits
```

这里的 `P0` 是最开始的：
$$
P0 = u \oplus v
$$
注意，不是 prefix 更新之后的 $P$。

# 10. 并行 prefix 怎么一步步得到这个 G？

初始：

```
i:    7 6 5 4 3 2 1 0
G:    0 0 0 0 0 1 0 1
P:    0 0 0 0 1 0 1 0
```

这里的 $G$ 还只是每一位自己的 generate。

------

## 第 1 轮：offset = 1

每个 bit $i$ 吸收 bit $i-1$ 的信息：
$$
G_i' = G_i \lor (P_i \land G_{i-1})
$$
看几个关键位。

### bit1

原来：
$$
G_1=0,\quad P_1=1,\quad G_0=1
$$
所以：
$$
G_1'=0\lor(1\land1)=1
$$
含义是：

> bit1 自己不产生进位，但是 bit0 产生了进位，并且 bit1 会传播，所以 bit0~bit1 这段会向 bit2 产生进位。

这对应：
$$
c_2=1
$$

### bit2

原来：
$$
G_2=1
$$
它自己就产生进位，所以：
$$
G_2'=1
$$

### bit3

原来：
$$
G_3=0,\quad P_3=1,\quad G_2=1
$$
所以：
$$
G_3'=0\lor(1\land1)=1
$$
含义是：

> bit2 产生的进位可以被 bit3 传播出去，所以 bit2~bit3 这段会向 bit4 产生进位。

第 1 轮结束后，大概得到：

```
G:    0 0 0 0 1 1 1 1
```

但注意，这时每个位置只知道最多 2 位范围，还不是从 bit0 开始的完整前缀。

------

## 第 2 轮：offset = 2

现在每个 bit $i$ 吸收 bit $i-2$ 的区间信息。

公式还是：
$$
G_i' = G_i \lor (P_i \land G_{i-2})
$$
这一步会把 2 位区间合成 4 位区间。

重点看 bit3。

第 1 轮后，bit3 已经知道 bit2~bit3 这段会不会产生进位。

现在 offset=2，它要合并 bit0~bit1 的信息。

也就是说 bit3 最终会知道：

```
bit0~bit3 这一整段会不会产生 carry
```

这正是：
$$
c_4
$$
在我们的例子里：

```
bit0 产生 carry
bit1 传播
bit2 产生 carry
bit3 传播
```

最终 bit0~bit3 整段会向 bit4 产生 carry，所以：
$$
G_3=1
$$
同理，bit4 会知道 bit1~bit4 的情况，但是由于 bit4 不传播，后面 carry 断掉。

第 2 轮结束后，有效前缀基本已经把低 4 位的 carry 算出来了：

```
G[0]=1
G[1]=1
G[2]=1
G[3]=1
```

------

## 第 3 轮：offset = 4

8-bit 最后一轮，每个 bit $i$ 吸收 bit $i-4$ 的信息。

对于 bit7，它会知道 bit0~bit7 整段的信息。

对于这个例子，高位全是 0，也不会传播，所以最终：

```
G = 00001111
```

对应 carry：

```
G[0]=c1=1
G[1]=c2=1
G[2]=c3=1
G[3]=c4=1
G[4]=c5=0
G[5]=c6=0
G[6]=c7=0
G[7]=c8=0
```

# 13. 为什么这适合安全计算？

因为普通串行 carry 是：

```
c1 depends on c0
c2 depends on c1
c3 depends on c2
...
c64 depends on c63
```

这会导致 64 层依赖。

而并行 prefix 是：

```
offset = 1
offset = 2
offset = 4
offset = 8
offset = 16
offset = 32
```

只有 6 层。

每一层里，所有 bit 的合并都可以同时做。

对安全计算来说，AND / OR 是昂贵的，XOR 是便宜的。并行前缀不能减少总门数到最低，但它极大减少了**交互轮数 / 电路深度**。这也是论文里 bitwise sum / carry 模块被拿来做比较协议的原因：它把“加法进位链”从线性传播变成并行传播。DOPM 论文中也明确把这个 bitwise sum 作为比较协议中的关键步骤：先得到 $u,v$ 的二进制共享，再调用 bitwise sum 得到 $s$ 的共享，最后用最高位判断比较关系。

# 14. 最后给你一个实现脑图

你让 Codex 实现时，可以让它牢牢记住下面这个结构：

```
输入：
    u_share, v_share       # XOR-shared uint64

第一步：
    P0 = u XOR v           # 原始 propagate，用于最后算 sum
    G  = u AND v           # generate
    P  = P0                # prefix propagate

第二步：
    for offset in [1,2,4,8,16,32]:
        oldG = G
        oldP = P

        shiftedG = oldG << offset
        shiftedP = oldP << offset

        G = oldG OR (oldP AND shiftedG)
        P = oldP AND shiftedP

第三步：
    carry_into = G << 1
    sum_low64 = P0 XOR carry_into
    carry64 = bit(G, 63)

输出：
    sum_low64_share
    carry64_share
```

一句话理解：

> $G$ 最开始表示“每一位自己是否产生 carry”；每经过一轮 prefix，它表示的区间长度翻倍；6 轮后，$G_i$ 就表示从 bit0 到 bit$i$ 是否整体产生 carry，也就是 $c_{i+1}$。然后左移一位当作每一位的输入 carry，和原始 $u\oplus v$ 异或，就得到 sum。





就是每一轮两两合并是吗？最后能得到最后一位的进位，但是过程中，有些地方的c是不是没拿到啊a

已思考几秒

对，你理解得基本对：**每一轮是在“两两合并区间”**，但不是固定相邻两个 bit 永远合并，而是按距离翻倍合并：

```
第 1 轮 offset=1：合并相邻 1-bit 区间
第 2 轮 offset=2：合并相邻 2-bit 区间
第 3 轮 offset=4：合并相邻 4-bit 区间
第 4 轮 offset=8：合并相邻 8-bit 区间
...
```

但是你问的重点非常关键：

> 过程中有些地方的 c 是不是没拿到？

答案是：**过程中确实有些位置还没拿到“真正从 bit0 传上来的 carry”，但最终一轮结束后，所有位置的 carry 都拿到了。**

------

## 1. 中间轮的 $G_i$ 不一定等于真正的 $c_{i+1}$

初始时：
$$
G_i = g_i = u_i \land v_i
$$
这个只表示：

> 第 $i$ 位自己会不会产生 carry。

它还不是：
$$
c_{i+1}
$$
因为真正的：
$$
c_{i+1}
$$
表示的是：

> 从 bit0 一路加到 bit$i$ 之后，是否会向 bit$i+1$ 产生进位。

这需要知道 bit0 到 bit$i$ 的整体情况。

------

## 2. 每一轮 $G_i$ 覆盖的区间越来越大

以 8-bit 为例。

初始：

```
G[i] 只知道 bit i 自己
```

也就是：

```
G0 知道 bit0
G1 知道 bit1
G2 知道 bit2
G3 知道 bit3
...
```

第 1 轮 offset=1 后：

```
G1 知道 bit0~bit1
G2 知道 bit1~bit2
G3 知道 bit2~bit3
G4 知道 bit3~bit4
...
```

注意，这时候：

```
G3 知道的是 bit2~bit3
```

但真正的：
$$
c_4
$$
需要知道：

```
bit0~bit3
```

所以第 1 轮后：
$$
G_3 \neq c_4
$$
它只是一个**局部区间 carry**，还不是从最低位开始的完整 carry。

------

## 3. 第 2 轮后，覆盖范围翻倍

第 2 轮 offset=2 后：

```
G3 知道 bit0~bit3
G4 知道 bit1~bit4
G5 知道 bit2~bit5
...
```

这时：

```
G3 = c4
```

因为它终于覆盖了 bit0 到 bit3。

但：

```
G5
```

这时只知道 bit2~bit5，不知道 bit0~bit5，所以：

```
G5 还不是 c6
```

------

## 4. 第 3 轮后，8-bit 全部 carry 都拿到了

第 3 轮 offset=4 后：

```
G7 知道 bit0~bit7
G6 知道 bit0~bit6
G5 知道 bit0~bit5
...
```

这时候所有位置都已经覆盖到 bit0，所以：
$$
G_0 = c_1
$$
一直到：
$$
G_7 = c_8
$$
所以最终：

```
G[i] = c[i+1]
```

这时候所有 carry 都拿到了。

------

## 5. 64-bit 也是一样

64-bit 需要 6 轮：

```
offset = 1
offset = 2
offset = 4
offset = 8
offset = 16
offset = 32
```

每一轮覆盖范围翻倍：

```
初始：覆盖 1 位
第 1 轮：覆盖 2 位
第 2 轮：覆盖 4 位
第 3 轮：覆盖 8 位
第 4 轮：覆盖 16 位
第 5 轮：覆盖 32 位
第 6 轮：覆盖 64 位
```

所以第 6 轮结束后：

```
G[0]  = c1
G[1]  = c2
G[2]  = c3
...
G[62] = c63
G[63] = c64
```

因此不只是最后一位 carry 拿到了，**所有中间 carry 也都拿到了**。

## 6. 你疑惑的点可以这么理解

你现在感觉：

> 每轮两两合并，那是不是只保证最后能得到最后 carry，中间有些 carry 没算全？

这个担心是对的，但要区分两种 prefix 电路。

### 情况 A：只算最终 carry

如果你只构造一棵归约树：

```
bit0~bit1
bit2~bit3
bit4~bit5
bit6~bit7

然后合并成：
bit0~bit3
bit4~bit7

最后合并成：
bit0~bit7
```

那确实只能直接得到最终 carry：

```
c8
```

中间的：

```
c1,c2,c3,c4,c5,c6,c7
```

不会全部得到。

这种像 reduction tree，只关心最终结果。

### 情况 B：Kogge-Stone / parallel-prefix

我们前面讲的这个不是只做一棵总归约树，而是对每个位置都做 prefix。

也就是说：

```
G1 最终要知道 bit0~bit1
G2 最终要知道 bit0~bit2
G3 最终要知道 bit0~bit3
G4 最终要知道 bit0~bit4
...
G63 最终要知道 bit0~bit63
```

所以它最终能得到所有 carry。

这个叫 parallel-prefix，不是单纯 reduction。

## 8. 这也是为什么 sum 可以一次性算出来

因为 sum 每一位需要：
$$
s_i = p_i \oplus c_i
$$
如果我们只知道最后的：
$$
c_{64}
$$
那没法算完整的 sum。

但 parallel-prefix 最后得到的是：

```
G0 = c1
G1 = c2
G2 = c3
...
G63 = c64
```

所以把 $G$ 左移一位：

```
carry_into = G << 1
```

就得到：

```
carry_into[0]  = c0 = 0
carry_into[1]  = c1 = G0
carry_into[2]  = c2 = G1
...
carry_into[63] = c63 = G62
```

然后：

```
sum = P0 XOR carry_into
```

就能把所有 sum bit 一次性算出来。

------

## 9. 你可以这么记

最关键一句：

> 并行进位不是“只把所有 bit 合成一个最终 carry”，而是“给每一个 bit 都算出从 bit0 到它为止的 prefix carry”。

所以：

```
中间轮：有些 G_i 只是局部区间 carry，不一定是真 c
最终轮：所有 G_i 都覆盖 bit0，因此全部是真 c
```

这就是你刚才疑惑的那个点
